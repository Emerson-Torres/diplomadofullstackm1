fetch y códigos HTTP: ¿dónde cae el 400, el 409 y el 500?

Manejo de respuestas HTTP en un endpoint de creación de usuarios con CodeIgniter 4 y cómo consumirlo correctamente con fetch en JavaScript.

⚙️ CodeIgniter 4 📚 JavaScript — fetch API 📡 HTTP 200 · 400 · 409 · 500 📅 Clase práctica
1 Qué hace el endpoint y por qué usa 400 vs 409

🗄️ Contexto del backend — Admin::createUser()

El método createUser() del controlador app/Controllers/Admin.php recibe datos de un formulario de registro y sigue tres fases de validación antes de insertar el usuario:

400
Bad Request — validación de formato

Los campos de entrada son vacíos, mal formados o muy cortos. El problema está en lo que el cliente envió, sin llegar a la base de datos.

409
Conflict — conflicto de unicidad

Los datos tienen formato correcto pero colisionan con un registro ya existente en la base de datos (email o username duplicado).

200
OK — inserción exitosa

Todas las validaciones pasaron y el usuario fue creado. Devuelve el nuevo id, username y email.

500
Internal Server Error

Excepción inesperada en el servidor (fallo de BD, error de configuración, etc.). El cliente no tiene culpa.

📄 Código real del controlador (CI4)

PHP — app/Controllers/Admin.php 
public function createUser(): ResponseInterface
{
    // ── Leer campos del POST ─────────────────────────────────────
    $username         = trim((string) $this->request->getPost('username'));
    $email            = trim((string) $this->request->getPost('email'));
    $password         = trim((string) ($this->request->getPost('password') ?? ''));
    // ... otros campos opcionales (nombres, apellidos, linkedin, cargo...)

    // ── FASE 1: Validación de formato → 400 ─────────────────────
    if ($username === '') {
        return $this->respond(['error' => 'El nombre de usuario es obligatorio'], 400);
    }
    if ($email === '' || !filter_var($email, FILTER_VALIDATE_EMAIL)) {
        return $this->respond(['error' => 'Se requiere un email válido'], 400);
    }
    if ($password === '' || strlen($password) < 8) {
        return $this->respond(['error' => 'La contraseña debe tener al menos 8 caracteres'], 400);
    }

    try {
        $userModel = new UserModel();

        // ── FASE 2: Conflictos de unicidad → 409 ────────────────────
        if ($userModel->where('email', $email)->first()) {
            return $this->respond(['error' => 'El email ya está en uso'], 409);
        }
        if ($userModel->where('username', $username)->first()) {
            return $this->respond(['error' => 'El nombre de usuario ya está en uso'], 409);
        }

        // ── FASE 3: Insertar usuario → 200 ──────────────────────────
        $id = $userModel->insert([
            'username'  => $username,
            'email'     => $email,
            'password'  => password_hash($password, PASSWORD_DEFAULT),
            // ... otros campos opcionales
        ]);
        return $this->respond(['data' => ['id' => $id, 'username' => $username, 'email' => $email]], 200);

    } catch (\Throwable $e) {
        // ── FASE 4: Excepción interna → 500 ─────────────────────────
        return $this->respond(['error' => 'No se pudo crear el usuario'], 500);
    }
}
ℹ️ ¿Por qué 400 y no 422?
400 (Bad Request) es la respuesta semánticamente correcta cuando los datos de entrada no cumplen las reglas del servidor. Algunos equipos prefieren 422 (Unprocessable Entity) para errores de validación, pero 400 es igualmente válido y más universal.
2 Cómo funciona try / catch con fetch — la regla de oro

🎯 La pregunta clave

«Cuando el servidor responde 400 o 409, ¿el código entra al try o al catch?»

Respuesta directa: entra al try.
fetch solo lanza una excepción (y va al catch) en casos de error de red, no por códigos HTTP 4xx o 5xx.

Esto significa que con el código incorrecto, un 400 o un 409 parecería una respuesta exitosa:

JavaScript — ❌ Código problemático (NO usar así) 
async function peticion() {
  try {
    const res  = await fetch("https://miapi.com/api/users");
    const data = await res.json();

    mostrar(data); // ← PROBLEMA: si res.status es 400 o 409,
                   //   data.error contiene el mensaje de error del servidor
                   //   pero este código lo trata como si fuera un éxito
  } catch (error) {
    // Aquí solo llegan errores de RED
    // Un 400 o 409 NUNCA llega aquí → el mensaje de error del servidor se pierde
    mostrarError("No se pudo cargar. Intenta de nuevo.");
  }
}

// ¿Qué pasa cuando el servidor responde 409?
// → res.status === 409  (pero no lo chequeamos)
// → data = { "error": "El email ya está en uso" }
// → mostrar(data) recibe el error como si fuera datos válidos ← BUG
⚠️ Conclusión: si no validamos res.ok o res.status dentro del try, los errores 400, 409 y 500 del servidor llegan silenciosamente como "datos normales" y el frontend nunca muestra el mensaje de error correcto.

Código HTTP Significado ¿try o catch? Causa del error Mensaje recomendado al usuario
200 OK Usuario creado exitosamente try ✓ — «✅ Usuario creado. Bienvenido, {username}.»
400 Bad Request Datos inválidos o incompletos try ✓ username vacío, email inválido, password corta Mostrar data.error tal como llega del servidor:
«El nombre de usuario es obligatorio»
«Se requiere un email válido»
«La contraseña debe tener al menos 8 caracteres»
409 Conflict Conflicto de unicidad en BD try ✓ Email o username ya registrado Mostrar data.error:
«El email ya está en uso»
«El nombre de usuario ya está en uso»
401 Unauthorized No autenticado try ✓ Token inválido o sesión expirada «Tu sesión expiró. Inicia sesión nuevamente.»
500 Server Error Error interno del servidor try ✓ Fallo de BD, excepción no controlada «Ocurrió un error en el servidor. Intenta más tarde.»
Error de red Sin conexión / CORS / DNS / timeout catch ✗ La solicitud nunca llegó al servidor «Sin conexión. Verifica tu red e intenta de nuevo.»
💡 Regla mnemónica:
catch = el servidor ni siquiera vio la petición (red rota).
try = el servidor respondió algo — sea 200, 400, 409 o 500.
4 Implementación recomendada — código JS completo

✅ Versión corregida y profesional de peticion()

Incorpora: POST, Content-Type: application/json, JSON.stringify, lectura segura de la respuesta, manejo explícito por status y fallback para errores de red.

JavaScript — implementación recomendada 
/**
 * Crea un usuario llamando al endpoint de CI4.
 * Maneja correctamente todas las respuestas HTTP posibles.
 */
async function crearUsuario(formData) {
  try {

    // 1. Realizar la petición POST con headers y body correctos
    const res = await fetch("https://miapi.com/api/users", {
      method:  "POST",
      headers: { "Content-Type": "application/json" },
      body:    JSON.stringify({
        username: formData.username,
        email:    formData.email,
        password: formData.password,
        nombres:  formData.nombres  || "",
        apellidos: formData.apellidos || "",
      }),
    });

    // 2. Leer el JSON de forma segura (aunque el servidor no envíe JSON válido)
    let data;
    try {
      data = await res.json();
    } catch (_) {
      data = {};  // fallback si la respuesta no es JSON
    }

    // 3. Despachar por código HTTP — TODOS entran aquí (try), no al catch
    if (res.status === 200) {
      // ✅ Éxito: { "data": { "id": 7, "username": "ana", "email": "ana@..." } }
      mostrarExito(`✅ Usuario "${data.data.username}" creado con ID ${data.data.id}`);
      return data.data;
    }

    if (res.status === 400) {
      // ⚠️ Validación: { "error": "El nombre de usuario es obligatorio" }
      //               { "error": "Se requiere un email válido" }
      //               { "error": "La contraseña debe tener al menos 8 caracteres" }
      mostrarError(data.error || "Datos inválidos. Revisa el formulario.");
      return null;
    }

    if (res.status === 409) {
      // 🔴 Conflicto: { "error": "El email ya está en uso" }
      //              { "error": "El nombre de usuario ya está en uso" }
      mostrarError(data.error || "Ya existe un usuario con esos datos.");
      return null;
    }

    if (res.status === 401) {
      // 🔒 No autenticado
      mostrarError("Tu sesión expiró. Inicia sesión nuevamente.");
      window.location.href = "/login";
      return null;
    }

    if (res.status === 500) {
      // 💥 Error interno: { "error": "No se pudo crear el usuario" }
      mostrarError("Ocurrió un error en el servidor. Intenta más tarde.");
      return null;
    }

    // Cualquier otro código no contemplado
    mostrarError(`Error inesperado del servidor (HTTP ${res.status})`);
    return null;

  } catch (error) {
    // 📡 Solo llega aquí si FALLÓ LA RED (sin conexión, CORS, DNS, timeout)
    // Un 400 o 409 NUNCA llega aquí
    mostrarError("Sin conexión. Verifica tu red e intenta de nuevo.");
    console.error("[red]", error);
    return null;
  }
}

// ── Helpers de UI de ejemplo ─────────────────────────────────
function mostrarExito(msg) {
  document.getElementById("resultado").innerHTML =
    `<p style="color:#059669">${msg}</p>`;
}
function mostrarError(msg) {
  document.getElementById("resultado").innerHTML =
    `<p style="color:#dc2626">${msg}</p>`;
}

6 Errores comunes en la integración frontend-backend
❌ Error 1 — «Creer que un 400 o 409 cae en catch»
El error de validación llega al try, no al catch. Si verificas los errores solo en el catch, nunca verás los mensajes del servidor para 400/409.
❌ Incorrecto
try {
  const res  = await fetch(...);
  const data = await res.json();
  mostrar(data); // ← data puede ser { error: "El email ya está en uso" }
                 //   pero lo mostramos como si fuera éxito
} catch (error) {
  mostrarError("Error"); // ← aquí NUNCA llega un 400, 409 o 500
}
⚠️ Error 2 — No leer el JSON de la respuesta de error
Cuando el servidor responde 400 o 409, el cuerpo de la respuesta contiene el mensaje de error útil para el usuario (data.error). Si no llamas await res.json(), pierdes ese mensaje.
❌ Incorrecto vs ✅ Correcto
// ✗ Pierdes el mensaje del servidor
if (!res.ok) {
  mostrarError("Algo salió mal"); // mensaje genérico e inútil
}

// ✓ Lees y muestras el mensaje exacto del servidor
if (!res.ok) {
  const err = await res.json();
  mostrarError(err.error); // "El email ya está en uso" ← útil para el usuario
}
💡 Error 3 — Olvidar el segundo await para .json()
res.json() retorna una Promesa, no el objeto final. Sin await, data es una Promesa y data.error será undefined.
❌ Incorrecto vs ✅ Correcto
// ✗ data es una Promesa, no el objeto JSON
const data = res.json();            // falta await ← bug silencioso
console.log(data.error);          // undefined

// ✓ data es el objeto JavaScript real
const data = await res.json();     // correcto
console.log(data.error);          // "El email ya está en uso"
💬 Error 4 — Usar res.ok como único control (sin leer el status)
res.ok es true solo para códigos 200–299. Esto te dice que algo falló, pero no te dice qué tipo de error fue. Siempre es mejor disparchar por res.status para dar mensajes específicos.
⚠️ Funciona pero es genérico vs ✅ Específico y útil
// ⚠️ Funciona, pero mensaje genérico para cualquier error
if (!res.ok) {
  mostrarError("Error del servidor"); // igual para 400, 409, 500, 401...
}

// ✓ Específico por código → mejor UX
if      (res.status === 400) mostrarError(data.error);
else if (res.status === 409) mostrarConflicto(data.error);
else if (res.status === 500) mostrarError("Error interno del servidor");
7 Checklist de integración frontend ↔ backend

📋 Antes de dar por terminada la integración, verifica:

  • ✓ Usas method: "POST" y headers: { "Content-Type": "application/json" } en la petición.
  • ✓ El body está serializado con JSON.stringify({...}) y contiene todos los campos obligatorios.
  • ✓ Llamas await res.json() (con los dos await: uno para fetch y otro para .json()).
  • ✓ Dentro del try validas res.status explícitamente para 200, 400, 409, 401 y 500.
  • ✓ Para 400 y 409 muestras data.error directamente al usuario (es el mensaje del servidor).
  • ✓ El bloque catch solo maneja errores de red (sin conexión, timeout) con un mensaje genérico de conectividad.
  • ✓ Probaste el endpoint con Postman/Insomnia enviando datos inválidos y verificaste que el JSON de error llega correctamente.
  • ✓ Verificaste en la pestaña Network de DevTools que los status codes 400 y 409 aparecen en rojo (son respuestas reales, no errores de red).
  • ✓ El formulario muestra el mensaje de error del servidor junto al campo correspondiente (no solo en un alert genérico).
  • ✓ El CI4 responde con la cabecera Content-Type: application/json en todos los casos (incluyendo los errores). Esto lo maneja automáticamente el método $this->respond().
🏆 Flujo de depuración recomendado cuando algo falla:
1. Abre DevTools → pestaña Network → haz la petición.
2. Haz clic en la petición → revisa Status (¿es 400? ¿409? ¿500?).
3. Pestaña Response → verifica el JSON que devolvió el servidor.
4. Si el status está ahí, el problema está en tu código JS (no en el servidor).
5. Si no llegó petición, revisa la URL y el CORS.
